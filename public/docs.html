Azure DevOps Authentication

Personal Access Token (PAT) Setup & Scopes

Azure DevOps offers over 30 distinct permission scopes. For security and least-privilege adherence, X-Factory only requests the minimal permissions necessary to read work items, discover repositories, and publish status checkmarks.

Zero-PAT Alternative Available
If you are logged into Azure CLI on your local machine (az login), X-Factory automatically uses your active session token. You do not need to create or store a static PAT!

1. Required & Recommended Scope Matrix

Scope Group Permission Level Status Why X-Factory Needs It
Work Items Read Required Executes WIQL queries to read ticket backlogs and acceptance criteria (Work Items: Read).
Code Read Required Allows online repository discovery and connectivity validation via Azure Repos REST API.
Code Status Recommended Enables publishing automated verification and review status checkmarks (Code: Status) to Azure commits and PRs.
Code Read & write Optional Only needed if pushing branches or creating PRs directly over HTTPS with the PAT.
All Other Scopes (25+) None Do Not Select Build, Release, Pipelines, User Profile, Tokens, Security, and Graph scopes are never needed.
Principle of Least Privilege: Avoid "Work Items: Read & write"
X-Factory never modifies, closes, or deletes work items in Azure DevOps. To protect your backlog from accidental state mutation or token compromise, select Work Items (Read) only. X-Factory's connection probe will flag tokens containing Work Items: Write as over-privileged.

2. Step-by-Step PAT Creation in Azure DevOps

  1. Log in to your Azure DevOps organization (e.g. https://dev.azure.com/your-org).
  2. In the upper-right corner of the portal, click the User settings icon (gear with person) and select Personal access tokens.
  3. Click + New Token.
  4. Enter a descriptive name (e.g. X-Factory Workbench).
  5. In the Organization dropdown, select your specific organization rather than All accessible organizations.
  6. Set an Expiration date according to your security policy (e.g. 60 or 90 days).
  7. Under Scopes, select Custom defined, click Show all scopes, and check:
    • Work Items: Check Read.
    • Code: Check Read and Status.
  8. Click Create and immediately copy your token. Paste it into the X-Factory Onboarding Wizard or Project Settings.

3. Troubleshooting Azure Token Errors

HTTP 401 Unauthorized

The PAT is expired, revoked, or missing the exact scope required for the requested resource (e.g. attempting WIQL without Work Items: Read). Generate a fresh PAT with the required scopes.

HTTP 403 Forbidden

The token is authenticated, but your user account lacks permission in the project (e.g. Stakeholder license attempting to view code, or repository-level ACL restriction). Confirm project reader permissions with your Azure administrator.

Jira Software Integration

Jira API Tokens

For Jira Cloud integration, generate an API token from your Atlassian account (id.atlassian.com → Security → API tokens).

  • Atlassian Host: Your cloud instance URL (e.g. https://your-domain.atlassian.net).
  • Email: The account email associated with the API token.
  • Project Key: The Jira project key (e.g. PROJ).
  • Permissions: The account requires read access to issues and JQL search across the project.
Source Repository Hosting

Git Hosting Providers & Mixing Stacks

Teams frequently split their development tools — for instance, managing sprint tickets in Jira Software while hosting source code and pull requests in GitHub or Azure Repos. X-Factory natively separates your issue tracker configuration from your Git repository host.

Jira + GitHub / GitLab

Queries Jira boards with JQL for backlog work items. When delivering verified code, pushes to GitHub/GitLab and creates a Pull Request referencing the Jira ticket key (e.g. [X-Factory] PROJ-101: Summary).

Azure DevOps + Azure Repos

Unified setup: queries Azure DevOps Boards with WIQL, verifies against local clones or remote branches, publishes status badges to commits using Code: Status, and creates Azure Repos PRs.

Local Only / Self-Hosted Git

Scans your local workspace folder directly. Requires zero online repository tokens or remote credentials. Isolated worktrees are created and verified entirely offline.

Issue Tracker Taxonomy & Standards

Ticket Workflow: Tags vs. Labels

X-Factory continuously scans your configured issue tracker to pull active, actionable work items into the Work Queue. To trigger automatic ingestion, tickets must be marked with the keyword agentic-workflow.

Provider Best Practice
Always use the native taxonomy term for each platform. In Azure DevOps, use native Tags. In GitHub and Jira, use native Labels.
Issue Tracker Taxonomy Where to Apply in Tracker Ingestion Mechanism
Azure DevOps
Tag Click + Add Tag directly beneath the work item title and type agentic-workflow. WIQL strictly queries [System.Tags] CONTAINS 'agentic-workflow'.
GitHub Issues
Label Assign agentic-workflow from the Labels selector on the right sidebar of the issue. REST API query for open issues with label:agentic-workflow.
Jira Software
Label Add agentic-workflow to the standard Labels input field on the Jira issue. JQL search: labels = 'agentic-workflow' AND statusCategory != Done.

Why Azure DevOps Uses Tags Instead of Labels

In GitHub and Jira, "Label" is the native first-class classification construct. In contrast, Azure DevOps does not have a native "Label" field — its built-in, first-class taxonomy is Tags (System.Tags). Standardizing on native Tags provides key benefits:

  • Universal Support: Built-in across every work item type (User Story, Bug, Task, Feature, Epic) without needing custom XML/process template modifications.
  • First-Class Board Filtering: Azure Boards includes a native "Filter by tag" widget at the top right of Kanban and sprint boards.
  • Visual Card Styling: You can define card style rules in Azure Boards (Board Settings → Styles) to automatically tint or highlight cards tagged with agentic-workflow.
  • Autocomplete: Typing ag into + Add Tag automatically autocompletes agentic-workflow for team members.
Strict Tag Enforcement

To guarantee consistent UX across your team and prevent unintended tickets from entering the queue, X-Factory strictly enforces the native Tag on Azure DevOps work items. Custom form fields (such as a custom field named Label) are ignored.

Safety Standard

Principle of Least Privilege & PR Safety

X-Factory is engineered around non-destructive, audited automation. To ensure team confidence and prevent rogue actions, the system operates under strict architectural guardrails:

Creation-Only PR Contract

X-Factory only ever commits code to isolated factory branches (factory/*), pushes the branch, and creates a Pull Request for human inspection. X-Factory strictly contains zero endpoints, CLI invocations, or permissions to close or merge pull requests. Merging remains 100% under human control.

Isolated Worktrees & Pollution Prevention

All agent execution occurs in isolated git worktrees stored outside your repository in ~/.x-factory/projects/<id>/worktrees/. Before any branch is committed, a strict baseline diff and pollution checker guarantees that unexpected temporary files, IDE artifacts, or credentials are never leaked into the repository.

Design System

Icon Design System & Anti-Drift Architecture

To ensure consistent branding, zero markup bloat, and unified dark/light theming, all icons in X-Factory follow a strict centralized SVG Sprite Sheet architecture. Inline SVGs and raw status emojis are strictly prohibited across the application.

1. Core Design System Rules

  • Zero Inline SVGs: Never write inline <svg><path.../></svg> in HTML or TypeScript templates.
  • Centralized Sprite Sheet: All icons are referenced from /assets/icons/sprite.svg#icon-{name} via <use href="...">.
  • Lucide 24×24 Standard: All icons use a 24×24 viewBox, 2px stroke width, rounded line caps and line joins (stroke-linecap="round" stroke-linejoin="round"), and fill="none".
  • Zero Raw Emojis: Status indicators must use standardized Lucide icons (e.g., check-circle-2, x-circle, loader-2 with .icon-spin).
  • Dynamic Theming: Icons automatically inherit their stroke color from CSS currentColor, guaranteeing flawless rendering across light and dark modes.

2. Usage in TypeScript Views & HTML

Use the typed helper functions exported from public/js/dom.ts:

TypeScript 
// HTML String Template
import { renderIcon } from "./dom";
const html = renderIcon("search", "sm");

// DOM Element Construction
import { createIconSvg } from "./dom";
const svgNode = createIconSvg("check-circle-2", "md", "icon-status-passed");
